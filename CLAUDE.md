**After any non-trivial change, run in order: clippy, then the CRAP gate, then format.** Each step gates the next; formatting is always last.

**1. Clippy.** Use `cargo clippy --workspace --all-targets`, not `cargo check` — the workspace opts into `clippy::pedantic`, so plain `check` is too lenient and gives a misleading "clean" answer. Confirm zero warnings before claiming code is clean. `cargo clippy --fix --allow-dirty` auto-applies most fixes; finish the rest manually. Real correctness flags (`cast_possible_truncation`, `cast_sign_loss`, etc.) warrant a fix; cosmetic pedantic flags on intentional code (e.g. `match_same_arms` on a documentation-style mapping table) can be `#[allow(...)]`'d with a justification comment.

**2. CRAP gate.** Run `just crap-ci`. CRAP = `cyclomatic² × (1 − coverage)³ + cyclomatic`; threshold is 30 (`.cargo-crap.toml`). It's slow because it instruments the suite under `llvm-cov`. It fails two ways — a baselined entry's CRAP regressed, or a function is newly above 30. Either is a real signal: fix by **adding test coverage** or **reducing cyclomatic complexity** (split big functions into small single-purpose helpers — the orchestrator stays untested but its branch count drops). Don't blindly run `just crap-baseline` to silence the gate — that bakes in complexity debt as accepted. Refresh the baseline only for genuinely grandfathered pre-existing entries, and say so in the commit message.

**Per-function coverage floor: every function must reach ≥90% line coverage** (the CRAP report's coverage column is per-function). Cover anything below it before moving on — extract untestable I/O so the logic is reachable, don't lower the bar. Typical gaps that keep a function under the bar: an error or `None` arm the happy path never hits (construct the error value directly instead of trying to provoke it through I/O), enum `From`/`TryFrom` impls that only exercise one variant, and match arms for inputs the tests never feed in.

**Run `just coverage` to check the floor** — it prints per-file line coverage and a per-function distribution histogram, then fails on anything that is *newly* below 90% or has got worse than `.coverage-baseline.json` records. That baseline works exactly like `.cargo-crap.json` and exists for the same reason: inherited debt must not be indistinguishable from debt added today, or the gate says the same thing on every run and stops meaning anything. A baselined function that reaches the floor is reported, not failed — refresh with `just coverage-baseline`, and only ever for genuinely inherited debt (say so in the commit message). Refreshing it to silence a function you just wrote bakes in precisely what the gate exists to catch.

**`just coverage-baseline` MERGES, keeping whichever reading is lower, and that is deliberate.** `llvm-cov` does not attribute lines identically across platforms: `clip` measures ≥97% on macOS and 87.5% on Linux. A baseline written from one machine is a file every machine has to satisfy, so a refresh that *replaced* the file dropped an entry Linux still needs and turned CI red on a "new" violation that was nothing of the kind — twice. Merging makes the file the union of everything ever seen, so a refresh can only ever be safe. It also means the local ratchet message ("N baselined functions now reach 90%") may be reporting a platform difference rather than an improvement; refreshing on that message is harmless, but it will not shrink the file.

**GOTCHA: cargo-crap's `coverage` field is a PERCENTAGE (0–100), not a fraction (0–1).** When querying `tmp/crap-now.json` by hand, the floor predicate is `select(.coverage < 90)` — `select(.coverage < 0.90)` silently tests 0.9% and reports everything as passing. Trust `just coverage`, not an ad-hoc jq threshold.

**2b. Large-file gate.** `just gate` also runs `just large-files`, which fails on any hand-written `.rs` under `crates/` over 30 KB. **Try compacting comments first** — this codebase's prose-heavy doc comments are 12–38% of a file, so tightening the wordy ones is often enough and costs nothing structural. Compact the wording, never the reasoning: a comment that records *why* something is the way it is was usually paid for in measurement. When even deleting every comment would leave the file over, it needs splitting into a directory module with an import-only `mod.rs`. Partitioning the test block is the expensive part, not moving the code — put each test with the rule it exercises and lift shared fixtures into their own `#[cfg(test)] mod`.

**3. Format.** Once clippy and CRAP are both green, run `cargo fmt --all` as the very last step before staging (default `rustfmt`, no `rustfmt.toml`). Do NOT run `cargo fmt` while iterating — it churns the diff and obscures what's changing under clippy/CRAP feedback. If it touches files you didn't edit, that's drift from elsewhere; commit those under their own focused message (e.g. `workspace: cargo fmt --all`), don't bundle with logic changes. `rustfmt` output is canonical, so letting it reformat the `.rs` files you touched is expected.

## Module structure

**`lib.rs` and every `mod.rs` are import-only.** They contain module declarations (`mod x;`) and re-exports (`pub use x::Y;`) — nothing else. No function, `impl`, `const`, or `static` definitions, and no `#[cfg(test)] mod tests`. Put logic (and its tests) in a named sibling submodule and surface it through a re-export. For example, a feature's event loop and dispatch live in its `runtime.rs`, and the feature's `mod.rs` only declares `mod runtime;` and re-exports `pub use runtime::run;`. When you find yourself adding a definition to a `mod.rs` or to `lib.rs`, create or extend a named submodule instead.
